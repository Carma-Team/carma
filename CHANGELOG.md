# Changelog

All notable changes to the CARMA HTTP contract and shared behaviour are recorded here.
Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions follow [SemVer](https://semver.org/).

## [Unreleased]

### Added
- **`UserOut` carries the DB-resolved business membership (CAR-258):** `businessMembershipRole` (`OWNER`/`MANAGER`/`CASHIER`) and `businessMembershipAmbiguous` are now on the payload every login, `POST /api/auth/refresh` and `GET /api/auth/me` return. `businessId`/`businessCategory`/`businessName`/`businessNameHe` are resolved from `business_memberships` too, not from the legacy `Business.owner_user_id` — so a MANAGER or CASHIER gets the same identity fields an OWNER already did. All five stay null with no membership; two or more memberships set `businessMembershipAmbiguous: true` instead of picking one, and every business field stays null, exactly like no membership — a DRIVER account with several memberships is unaffected otherwise. Resolved from the DB on every read, same as `/api/business/*` authorization (CAR-74), so a revoked or changed membership shows up on the very next request rather than waiting out the token's TTL. `generated.ts` regenerated; `web/src/lib/auth/types.ts`'s `AuthUser` gains the two new fields.
- **Browser session for the business web app (CAR-217):** `POST /api/auth/login` now also sets an httpOnly `carma_refresh` cookie (`Path=/api/auth`, `SameSite=Lax`), alongside its unchanged `{ token, user }` body. Two new endpoints trade that cookie for a session: `POST /api/auth/refresh` — rotates the cookie and returns a fresh, short-lived access token (`WEB_ACCESS_TOKEN_EXPIRES_MINUTES`, default 15) — and `POST /api/auth/logout`, which revokes it server-side and clears the cookie. Both require an `X-Requested-With: XMLHttpRequest` header (CSRF guard for a cookie-authenticated endpoint). New `refresh_tokens` table (migration `0016`), hashed and swept lazily like `otp_codes`; reuse of an already-rotated token revokes every other live session on the account. `CORS_ORIGINS` needs the web app's own origin to use any of this — a wildcard refuses credentialed requests by spec. Mobile is unaffected: unchanged login response, and it never calls the two new routes.
- **`web/` gains its sign-in flow:** `AuthProvider`/`useAuth` (session kept in memory only, never `localStorage`), `ProtectedRoute` (redirects to `/sign-in` without a valid session), and `lib/api/client.ts` for future authenticated calls (retries once on a 401 via a silent refresh). See `web/README.md`.
- **Friend requests (issue #32):** the endpoints the app has always called now exist — `POST`/`DELETE /api/users/:id/friend-request`, `GET /api/friend-requests`, `POST /api/friend-requests/:id/accept`, `DELETE /api/friend-requests/:id`, `DELETE /api/friends/:id`. A request is `pending` until the recipient answers, an accepted friendship counts for **both** users, and either side can unfriend. Sending a request to someone who already asked you accepts theirs instead of opening a second one.
- **`GET /api/users/search?phone=`** — find a driver to add. Matches `05…` and `+9725…` spellings of the same number (part of issue #21).
- **Invite links (issue #33):** `GET /api/users/me/invite` mints one stable code per user (`{INVITE_BASE_URL}/i/{code}`, 8 chars, no look-alike characters); `POST /api/invites/{code}/redeem` befriends whoever shared it — accepted outright, since handing out the link is the same consent as tapping accept. Migration `0008` adds `users.invite_code`. New `INVITE_BASE_URL` setting (default `https://carma.app`). Redeeming is idempotent and settles an already-open request. Note the code is reusable and not yet rotatable, so a forwarded link keeps working. Client contract: `invitesApi`; the deep-link config, landing page and share sheet are still to come.
- **`POST /api/users/match-contacts` (issue #33):** finds which of a user's contacts already drive with CARMA. Takes SHA-256 digests of canonical (E.164) numbers — raw numbers never leave the device — capped at 1000 per call, matched in memory, nothing persisted or logged. Each match carries `friendStatus` so the list can render the right button per row. Client contract: `userApi.matchContacts()`; the device-side hashing (needs `expo-crypto`) and the contacts UI are still to come.
- **Blocks moved to** `POST`/`DELETE /api/users/:id/block` (were `/api/leaderboard/block/:id`). Blocking now also drops a pending request, not just an accepted edge.
- **Scoring v2.1 (branch: feature/scoring-v2.1-telemetry):** server-side GPS telemetry analysis (`server/app/services/telemetry.py`) — independent detection of hard brakes, aggressive accelerations, and sharp turns from `route_waypoints`; event counts merged into scoring as `max(digest, gps)` so client under-detection can no longer produce a flat 100.
- **Speeding component activated:** time-over-threshold against a conservative absolute limit (120 km/h national max + 10 km/h GPS buffer); `has_speed_data=true` whenever waypoint coverage suffices. Sustained motorway speeding now costs score.
- **Telemetry confidence cap:** sparse/gappy GPS traces limit how far a trip can score above the driver's rolling score (upside only — reported events are never diluted). `apply_confidence()` in `scoring.py`.
- **Server-detected events persisted:** `Event` rows tagged `{"source": "server-gps"}` (incl. `SPEEDING` runs) give the trip map markers even before mobile sends its events array (issue #12).
- **`pointsCapped`** on the trip-save response (`TripOut` + `mobile/src/types/index.ts`) — tells the client the daily anti-grind caps reduced the award, instead of a silent 0.
- **`python -m app.seed --driver-scores-only`** — backfills NULL `users.driver_score` (the driver-score formula over each user's history) without reseeding; also runs automatically at the end of a full seed.
- **`distanceKm` on every leaderboard entry (CAR-173):** the driver's lifetime kilometres, so a client has a distance to divide `score` by. Read from the `users.total_distance` accumulator, which counts a trip as soon as it is saved — so it runs ahead of the COMPLETED-only sum behind `GET /api/users/:id/stats`, and the two legitimately disagree for a driver mid-trip. Settled to metres. `0.0` for a driver who has not driven yet, which is a real value rather than a missing one. The server does not rank on it: entries are still ordered and `rank`ed by total points.
- **`driveModeEnabled` is writable on `PATCH /api/users/me` (CAR-153):** automatic trip detection was readable on every profile fetch but nothing could set it, so a driver's choice never left the handset — and because the client merges the server's reply over its cached user, the column's permanent `false` would switch the setting back off on the next refresh once the app sends it. Only the keys present in the request are written, so a name change still leaves it alone. `generated.ts` regenerated to match. The Bluetooth device columns have the same gap and stay as they are on purpose — device selection belongs to the handset. Mobile does not send this field yet — that half is CAR-206.
- **`available` on every reward payload (CAR-47):** how many units are actually left. Derived per request from the redemptions ledger rather than stored — a unit is held while a voucher is live (`PENDING` inside its 5-minute TTL) and stays held once `USED`, so a lapsed voucher releases its unit with no job to run and no counter that can drift. `null` means unlimited, matching a `null` `stock`. Present on `GET /api/rewards`, `GET /api/vouchers`, `POST /api/rewards/:id/redeem` and the business reward routes. The server owns it; a client never sends one.

- **Password reset by phone code (CAR-60):** `POST /api/auth/password/reset/request` sends a code, `POST /api/auth/password/reset/confirm` takes the code plus a new password. No migration — `otp_codes.purpose` gains `PASSWORD_RESET`, kept apart from `LOGIN` so asking to reset does not void a login code mid-typing and neither code opens the other door. Single-use, 5-minute expiry, and completing one **clears `locked_until`** — a real unlock, where before a locked-out driver could only wait. A locked account still receives a reset code (unlike `otp/request`, which stays silent for one), because being locked out is the likeliest reason to be on that screen. No token comes back: a reset is not a sign-in. Both routes carry their own `5/minute` ceiling on top of the default. Only accounts that can actually sign in with a password (i.e. have an email) are eligible; a phone-only driver's way back in is `otp/request`. The number is matched in either spelling, `0501234567` or `+972501234567`.

### Removed
- **Instagram-style follow endpoints** (`GET`/`POST`/`DELETE /api/leaderboard/follow/:id`, `/api/leaderboard/requests…`). Nothing called them, and their auto-accept-on-public rule is what made friend requests invisible to public accounts. `mobile/src/services/api/leaderboard.api.ts` drops the matching dead methods; `userApi.sendFriendRequest` moved to `friendsApi.send`.

### Changed
- **Client-reported event severity is normalised at ingest (CAR-144).** `events.severity` held two populations on incompatible scales: a 4.5 m/s² brake stored as `0.36` if the phone detected it and `1.5` if the server did, and the old `[0, 100]` clamp made both legal, so nothing caught it. The server now maps client severity onto its own axis as it parses the events array — `1.0 + 2.0 × clamp(s, 0, 1)` — so every row in the column means the same thing whoever detected the event. On the wire this moves `EventOut.severity` for client-origin events: a `PHONE_USAGE` event that came back as `0.5` now comes back as `2.0`, and a hostile client sending `50` lands on `3.0` rather than `50`. The raw client number is untouched in `sensor_data`. The phone's SDK keeps its own 0-1 contract — a generic sensor library should not carry CARMA's weights — so the two sides meet at the server boundary instead. No backfill in this change: nothing renders severity and the scoring path is barred from reading it (CAR-155's guard), so nothing reads a stale row while it waits.
- **Leaderboard `type=friends`** now lists accepted friendships in either direction — previously only people the viewer had followed, so the user who accepted never saw the requester on their own board. `followStatus` on every entry means friendship status (the wire name is unchanged for the client).
- **Scoring v2.1 recalibration:** exponential-decay constants re-fit from recency-weighted live-fleet percentiles (`k_brake` 0.075→0.018, `k_accel` 0.089→0.022, `k_corner` 0.064→0.012, `k_speed` 0.045→0.012, `k_distraction` 0.112→0.020); `scoring_version` → `2.1.0`. Full-history re-score: median 84.3→88.5, p10 38.2→72.7, perfect-100 trips 6→0.
- **`stock` on a reward is now nullable, and `null` means unlimited (CAR-47).** It was `NOT NULL DEFAULT 0`, which conflated "unlimited", "sold out" and "never set" — harmless while nothing read the column, and not harmless the moment stock was enforced, because every reward created without an explicit stock would have read as sold out. Migration `0013` makes the column nullable, backfills the old zeros to `NULL`, and adds a CHECK. `stock` is the allocation the business committed to and is never decremented; what is left is `available`. Redeeming past the cap returns `409` with `{"code": "REWARD_OUT_OF_STOCK"}`.
- **The business dashboard shows `available/stock` (CAR-128)** — `3/5`, and `0/5` once the reward is gone. It rendered `stock` alone, which by design never moves, so an owner who allocated 5 units saw "5" whether none or all five had been claimed. An uncapped reward still reads "unlimited".
- **A route that never opted in can now answer `429` (CAR-126).** The default ceiling — 30 a minute and 500 an hour, per caller per endpoint — was declared when the limiter was written and enforced on nothing: under FastAPI 0.137 SlowAPI's middleware could no longer find the route it was about to limit, so it exempted every request. Only the seven routes carrying an explicit decorator were ever capped. There is nothing new for a client to handle — the reply is the shape the app already renders (`detail` and `retryAfterSeconds`, with `Retry-After`) — but a screen that has never seen a 429 can now see one. The health probes are exempt, and a counter follows the handler rather than the URL, so an id in the path no longer buys a fresh budget. The seven decorated routes are unchanged, and still count inside the handler — a request their validation or auth refuses first never reaches the counter.
- **A null on a profile field that cannot be null now answers `422` (found under CAR-153).** `PATCH /api/users/me` with an explicit `{"language": null}` or `{"isPrivate": null}` wrote the null straight to a NOT NULL column and came back as an unhandled `500`. Those fields are spelled `X | None` only so that "not sent" has a value — sending null was never meant to be legal. `name`, `age` and `city` are unaffected: their columns are nullable and clearing them is a real edit.
- **The per-number SMS cap no longer answers out loud on the two code-request routes (CAR-60).** `POST /api/auth/otp/request` and `POST /api/auth/password/reset/request` returned `429` once a number had spent its 5 codes an hour — and only a number with an account behind it can ever spend them, so the `429` itself answered "does this number have a CARMA account?", six requests from anyone who asked. Both routes now give the same reply whether a code went out or not; the cap is unchanged and still stops the sixth SMS, and `auth.otp.throttled` still records it for an operator. `POST /api/auth/otp/register` keeps its `429`, where a taken number already answers `409` and a driver signing up needs to know why no code arrived. The cost: a driver who spends the cap gets no explanation on screen.
- Monorepo at `Carma-Team/carma` — server, mobile, and mock-server live under one repo.

## [0.3.0] — 2026-06-13 — Beta improvements (branch: feature/beta-improvements)

### Added
- **Remove friend:** `-` button on the Friends leaderboard tab; confirmation dialog in Hebrew/English; optimistic UI removal with revert on failure. Mock server: `DELETE /api/friends/:userId`.
- **Server health check:** `services/api/health.api.ts` — `pingServer()` calls `GET /health/live`. `AppContext` pings on startup and shows a 6-second warning toast if the server is unreachable.
- **i18n:** `common.yes`, `common.no`, `common.serverUnreachable`, `leaderboard.removeFriendConfirm` added to `he.ts` and `en.ts`.
- **Render deployment config:** `USE_REAL_SERVER = true`, `STAGING_SERVER_URL = https://carma-app.onrender.com` in `serverConfig.ts` for real-device APK builds.

### Changed
- **Leaderboard rank display:** removed `#` prefix; top-3 ranks rendered in gold/silver/bronze colours; medal emojis removed.
- **GPS accuracy:** `SensorManager` switched from `Location.Accuracy.Balanced` to `Location.Accuracy.High` (GPS chip only — eliminates network/cell-tower position jumps).
- **Teleportation guard:** SDK `handleSensorUpdate` now caps each GPS tick's distance to `(speed/3600) × timeDeltaS × 1.5`. `timeDeltaS` is computed in `SensorManager` and passed via `onUpdate`.
- **Per-event cooldown:** reduced from 3 000 ms to 500 ms for all event types.
- **Event i18n keys** renamed to match UI spec: `hardBrakes → 'בלימה חזקה'`, `aggressiveAccels → 'האצה חריגה'`, `sharpTurns → 'פנייה חדה'`.

### Fixed
- **Phone touch on Home button:** added `sdk.on(DrivingEventType.PHONE_USAGE)` listener in `AppContext`; pressing the Home button mid-trip now increments the phone-touch counter (previously only in-app screen transitions were counted).

### Disabled (preserved, not deleted)
- **SWERVE detection (`EVT_SWERVE`):** all detection, scoring, and UI code commented out with `// EVT_SWERVE disabled` marker. `swerves` field made optional (`?`) in `TelemetryDigest`, `ValidTripPayload`, `ScoringInput` to keep TypeScript clean. Re-enable by searching for the marker and uncommenting.

### Deprecated
- `mock-server/` — Express + `db.json` stand-in. Use `server/` (FastAPI) as the real backend. The mock will be archived once the team has run on the real server for two weeks without falling back.
