# Internationalization (i18n)

CARMA's mobile app supports Hebrew and English. This document describes the mechanism as it exists today.

## The mechanism

Two resource files hold all static app copy, one per language:

- `mobile/src/i18n/he.ts` — Hebrew strings. This file is the source of truth: its shape defines the required key set.
- `mobile/src/i18n/en.ts` — English strings, typed against `he.ts` so it must provide the exact same nested keys.

Strings are grouped into namespaced, nested objects — `auth`, `dashboard`, `trip`, `marketplace`, `profile`, `common`, etc. — rather than one flat list or one file per message.

```ts
// i18n/he.ts
const he = {
  auth: { login: 'כניסה', logoutConfirm: 'האם אתה בטוח...' },
  common: { loading: 'טוען...', cancel: 'ביטול' },
} as const

export type TranslationKeys = typeof he
export type TranslationMap  = DeepString<TranslationKeys>
```

`en.ts` imports `TranslationMap` from `he.ts` and is typed as `TranslationMap` — so a missing key, or a key that isn't a string where Hebrew has one, is a **compile-time error**, not a silent runtime gap.

### Reading a string

`mobile/src/hooks/useTranslation.ts` exposes a `t(key)` function:

```ts
const { lang, setLang } = useApp()                       // 'he' | 'en', from AppContext
const translations = lang === 'he' ? he : en
t('auth.errors.emailRequired')                            // dot-path lookup into the object above
```

If a key doesn't resolve, `t()` returns the key path itself (e.g. `"auth.foo.bar"`) instead of throwing — a visible marker in dev builds rather than a crash.

### Language state

- Held in `AppContext` (`lang`, `setLang`).
- Persisted to `AsyncStorage` under `carma_lang`.
- Drives `direction` (`rtl`/`ltr`) at the root layout, and locale codes (`he-IL`/`en-US`) passed to `Intl`/`toLocaleDateString` calls around the app.

### What `t()` does not do

- **No pluralization** — the same string is used regardless of count.
- **No built-in interpolation** — placeholders like `{level}` or `{name}` (see `notifications.*`) are plain text tokens; call sites do their own `.replace()`. `t()` itself never substitutes anything.

### Guard against hardcoded copy

`eslint.config.js` runs a `no-restricted-syntax` rule across `src/**/*.{ts,tsx}` that flags any string or template literal containing Hebrew-range characters, outside `i18n/he.ts` itself and the bilingual-data-record files described below. `ci-mobile.yml` runs ESLint on every branch, so new UI copy written as a literal instead of through `t()` fails CI rather than shipping silently.

## A second, deliberate pattern: bilingual data records

Some content isn't app chrome — it's business data that inherently carries both languages on the record itself: reward categories, driver levels, server-provided voucher titles. These use paired fields (`labelHe`/`labelEn`, `nameEn`) directly on the object, resolved with a small helper:

```ts
// lib/utils.ts
export function localize(he: string, en: string | null | undefined, lang: string): string {
  return lang === 'he' ? he : (en || he)
}
```

Seen in `lib/constants.ts` (`DRIVER_LEVELS`, `REWARD_CATEGORIES`) and `MarketplaceScreen.tsx`. This is intentionally separate from `i18n/he.ts` + `en.ts` — those two files hold static UI copy; this pattern holds bilingual content that travels with a data record. It's a legitimate second mechanism, not a bug, **as long as both language fields are always populated.**

**Known gap:** `lib/constants.ts` — each level's `perks` array has Hebrew strings only (no `perksEn`). Not fixed here: `LevelConfig` (`types/index.ts`) mirrors the server's `LevelOut` schema, and `ci-mobile.yml`'s contract-drift check diffs it against the live OpenAPI spec — adding `perksEn` on the client needs a matching server-side change, not a mobile-only edit.

### Acceptable as-is

- `src/components/ui/LanguagePicker.tsx`, `src/screens/app/SettingsScreen.tsx` — the language picker shows each language's own endonym ("עברית" / "English"), not a translation of "Hebrew"/"English"; standard practice in language switchers, exempted from the lint rule with an inline comment.

## Summary

The two-file, nested-namespace resource pattern (`he.ts`/`en.ts` + a `t()` lookup) matches how the industry generally does this. Everything that previously bypassed it — `lib/utils.ts`'s formatters, `BluetoothSettings.tsx`, `ScoreChart.tsx`, and a handful of one-off literals in `RegisterScreen.tsx`, `LeaderboardScreen.tsx`, `RoadmapHero.tsx`, `ProfileScreen.tsx`, and `SettingsScreen.tsx` — has been moved into `he.ts`/`en.ts` and is now read through `t()`. The ESLint rule above is what keeps it that way going forward.

### Follow-up: country filtering removed from the leaderboard (CAR-22, CAR-44, CAR-20)

One of the caught literals was `LeaderboardScreen.tsx`'s `useState(user?.country ?? 'ישראל')` — a hardcoded default for a country picker. That picker was dead weight: the server never accepted a `country` filter (`GET /api/leaderboard` only takes `type`/`city`) and always returns a single pinned value (`COUNTRY = "ישראל"` in `server/app/services/leaderboard.py`, with a comment noting the country dimension is inherited from a retired mock server CARMA doesn't actually use). Removed from the mobile side: the `selectedCountry` state, the country `LocationPicker`, `handleCountryChange`, the `country` param in `leaderboard.api.ts`, and the now-unused `selectCountry`/`showing_national` i18n keys. The "national" tab still exists — it just no longer shows a picker, since there's nothing to pick.

This same removal is also covered by CAR-22/CAR-44/CAR-20 in the pending PR #108 (a separate, already-open UI-polish batch) — the two land independently since they're on different branches.

### Note: `formatDuration` keeps its hours branch (CAR-30)

`formatDuration`'s hours-rollover logic (`{hours}h {mins}m`, not just minutes) is intentional — it's the fix for CAR-30 ("formatDuration didn't show hours"), also tracked in PR #108. Don't simplify it back down to minutes-only when touching this function.
