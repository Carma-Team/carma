# Internationalization (i18n)

CARMA's mobile app supports Hebrew and English. This document describes the mechanism as it exists today.

## The mechanism

Two resource files hold all static app copy, one per language:

- `mobile/src/i18n/he.ts` — Hebrew strings. This file is the source of truth: its shape defines the required key set.
- `mobile/src/i18n/en.ts` — English strings, typed against `he.ts` so it must provide the exact same nested keys.

Strings are grouped into namespaced, nested objects — `auth`, `dashboard`, `trip`, `marketplace`, `profile`, `common`, etc. — rather than one flat list or one file per message.

```ts
// i18n/he.ts
const he = {
  auth: { login: 'כניסה', logoutConfirm: 'האם אתה בטוח...' },
  common: { loading: 'טוען...', cancel: 'ביטול' },
} as const

export type TranslationKeys = typeof he
export type TranslationMap  = DeepString<TranslationKeys>
```

`en.ts` imports `TranslationMap` from `he.ts` and is typed as `TranslationMap` — so a missing key, or a key that isn't a string where Hebrew has one, is a **compile-time error**, not a silent runtime gap.

### Reading a string

`mobile/src/hooks/useTranslation.ts` exposes a `t(key)` function:

```ts
const { lang, setLang } = useApp()                       // 'he' | 'en', from AppContext
const translations = lang === 'he' ? he : en
t('auth.errors.emailRequired')                            // dot-path lookup into the object above
```

If a key doesn't resolve, `t()` returns the key path itself (e.g. `"auth.foo.bar"`) instead of throwing — a visible marker in dev builds rather than a crash.

### Language state

- Held in `AppContext` (`lang`, `setLang`).
- Persisted to `AsyncStorage` under `carma_lang`.
- Drives `direction` (`rtl`/`ltr`) at the root layout, and locale codes (`he-IL`/`en-US`) passed to `Intl`/`toLocaleDateString` calls around the app.

### What `t()` does not do

- **No pluralization** — the same string is used regardless of count.
- **No built-in interpolation** — placeholders like `{level}` or `{name}` (see `notifications.*`) are plain text tokens; call sites do their own `.replace()`. `t()` itself never substitutes anything.
- **No lint/extraction tooling** — nothing currently fails CI if new UI copy is written as a literal instead of going through `t()`. The violations below exist because of this gap, not because the mechanism is misdesigned.

## A second, deliberate pattern: bilingual data records

Some content isn't app chrome — it's business data that inherently carries both languages on the record itself: reward categories, driver levels, server-provided voucher titles. These use paired fields (`labelHe`/`labelEn`, `nameEn`) directly on the object, resolved with a small helper:

```ts
// lib/utils.ts
export function localize(he: string, en: string | null | undefined, lang: string): string {
  return lang === 'he' ? he : (en || he)
}
```

Seen in `lib/constants.ts` (`DRIVER_LEVELS`, `REWARD_CATEGORIES`) and `MarketplaceScreen.tsx`. This is intentionally separate from `i18n/he.ts` + `en.ts` — those two files hold static UI copy; this pattern holds bilingual content that travels with a data record. It's a legitimate second mechanism, not a bug, **as long as both language fields are always populated.**

**Known gap:** `lib/constants.ts` — each level's `perks` array has Hebrew strings only (no `perksEn`), so perks show in Hebrew even when the app is in English.

## Violations of the primary mechanism

Hardcoded copy found in `mobile/src` that bypasses `i18n/he.ts` / `en.ts` entirely, or undermines it:

### Full bypass — hardcoded text shown regardless of `lang`

| File | What |
|---|---|
| `src/lib/utils.ts` (`formatPoints`, `formatDistance`, `formatDuration`, `formatDate`, `formatRelativeTime`) | Every one of these takes a `lang` argument and branches on it with **inline literal strings** (`נקודות`/`pts`, `ק"מ`/`km`, `דק'`/`שנ'`/`שע'`, `עכשיו`/`just now`, `לפני`/`ago`...) instead of reading from `he.ts`/`en.ts`. This is the exact anti-pattern you're asking to keep out of the codebase, and it's the widest-reaching instance — these functions are used for on-screen point/distance/duration labels across the app. |
| `src/screens/app/BluetoothSettings.tsx` | The entire screen is hardcoded Hebrew — every `<Text>`, both `addToast(...)` calls, and `Alert.alert('שגיאה', 'לא ניתן לשמור את ההגדרה')`. It doesn't call `useTranslation()` at all, so it always renders Hebrew regardless of the user's language setting. |
| `src/components/social/ScoreChart.tsx` | Takes a `lang: Language` prop but never uses it for text: month abbreviations, bucket labels ("תחילה"/"אמצע"/"לאחרונה"), granularity labels ("לפי יום"/"לפי שבוע"/"לפי חודש"), the chart title, empty state, and the "+X% improvement" line are all Hebrew literals. |
| `src/screens/auth/RegisterScreen.tsx:72-73` | The post-registration welcome toast (`ברוך הבא, ${firstName}! 🎉`) is a hardcoded Hebrew literal, even though the rest of this file uses `t()` correctly. |
| `src/screens/auth/RegisterScreen.tsx:89` | The city field's `placeholder: 'תל אביב'` is a literal, unlike every other field on the same line which uses `t(...)`. |
| `src/screens/app/LeaderboardScreen.tsx:214` | The friend-invite SMS body is one long hardcoded Hebrew sentence. |
| `src/components/gamification/RoadmapHero.tsx:42` | `` עוד {…} {t('common.points')} לרמה הבאה `` — mixes a real translation call with literal Hebrew words in the same sentence. |

### Weakened by a hardcoded fallback

`t(key) || 'ליטרל בעברית'` — if the key ever resolves to something falsy, or as dead-weight duplication, a hardcoded Hebrew string is shown regardless of `lang`:

- `src/screens/app/ProfileScreen.tsx:64,65,67,68`
- `src/screens/app/SettingsScreen.tsx:34`

### Acceptable as-is (flagged for completeness, not a fix)

- `src/components/ui/LanguagePicker.tsx` — language names in the picker ("עברית" / "English") are conventionally shown as each language's own endonym, not translated; this is standard practice in language switchers, not a violation.

## Summary

The two-file, nested-namespace resource pattern (`he.ts`/`en.ts` + a `t()` lookup) matches how the industry generally does this — see the note in chat for the comparison. The gap isn't the architecture; it's that nothing enforces it, so hardcoded strings have crept into a handful of files, concentrated in `lib/utils.ts`'s formatters and a couple of screens/components that were written without hooking up `useTranslation()` at all.
